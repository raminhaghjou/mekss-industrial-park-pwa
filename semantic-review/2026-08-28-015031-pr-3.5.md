# Database-backed authorization, typed management inputs, and atomic audit writes

Task 3.5 moves authorization decisions from stale JWT claims to the current user row, introduces bounded DTO validation for management endpoints, normalizes API failures, and puts the required lifecycle mutations and their success audits in interactive transactions. Advertisement moderation now uses a conditional pending-state transition, while dashboard and report queries retain an explicit empty scope for non-global actors. The design closes the main stale-role, duplicate-moderation, partial-audit, and zero-scope data-leak paths, but request correlation is not connected to audit records and one new DTO contract silently loses accepted data. A malformed but correctly signed JWT subject also reaches the database boundary without runtime validation.

Watch for: **[medium, confirmed]** audit rows produced by real management requests have no correlation ID; **[medium, confirmed]** factory-create fields accepted by validation are not persisted; **[low, likely]** a signed token with a missing or non-string `sub` becomes a DB/500 failure instead of a non-disclosing 401.

**Verdict**: NEEDS_CHANGES

## High-level view

`JwtAuthGuard` now treats the token as proof of signature/expiry only and rebuilds the principal from the database, so role and phone changes take effect on the next request and deleted, inactive, or unapproved users are rejected. Runtime claim shape is still trusted after signature verification, leaving malformed `sub` values outside the intended invalid-token path.

The reusable transaction helper runs the business mutation and `AuditService.record` on the same Prisma transaction client. This gives the required rollback behavior for user lifecycle, park CRUD, and advertisement creation/moderation, but no request-scoped correlation value is supplied by any production caller, so the new audit field cannot link those successful writes to an API request.

Management bodies and opaque IDs now pass through whitelist validation, with Prisma enums and bounded scalar/array fields represented explicitly. The factory-create DTO advertises several optional fields that the create service never maps, so valid input is accepted and silently discarded.

Advertisement moderation scopes park managers before a conditional `PENDING` update, making the second concurrent decision conflict without creating a second success audit; parkless advertisements do not match manager scope. Dashboard and report filters now use `factoryId in []` for non-global actors with no factories rather than dropping the predicate and querying globally.

## Database identity refresh leaves malformed claims outside the 401 boundary

Limiting the verification `try/catch` to JWT parsing keeps database outages out of the invalid-credential path, while rebuilding `request.user` from Prisma makes role changes and account revocation effective immediately.

**[low, likely]** The verified payload is only typed as `{ sub: string }`; no runtime check establishes that `sub` exists, is a string, or is non-empty before it becomes `where: { id: payload.sub }` in `auth.guard.ts`. A correctly signed JWT containing no `sub`, or a non-string `sub`, passes signature verification and reaches Prisma with an invalid unique selector. Prisma is expected to reject that selector outside the guard's catch, turning a malformed credential into the global 500 path rather than the required generic 401. Confirm the exact Prisma failure with a focused case, then reject the claim before lookup.

The guard tests cover stale-role replacement, deleted/inactive/unapproved users, DB failure propagation, malformed signatures, and explicit role denial. Not tested: a correctly signed token with missing, empty, or non-string `sub`.

## Transactional audit atomicity stops at request traceability

The transaction helper creates one atomic boundary:

```
management request
  -> Prisma interactive transaction
       -> business write / token revocation / relation update
       -> success audit through the same tx client
  -> commit, or roll back both
```

**[medium, confirmed]** `AuditService.record` can persist `correlationId`, but no production call site supplies one; the only production `correlationId:` assignment is inside `AuditService` itself. `auditedTransaction` omits correlation metadata, and `ApiExceptionFilter` derives or generates an ID only after an exception, too late for a successful mutation's audit row. Generate or validate a request ID before controller execution, attach it to request context, reuse it in the filter, and thread it into the transaction helper.

The audit tests verify correlation persistence only when it is explicitly supplied. Not tested: a management request carrying `X-Request-ID` through to its committed audit row, because no such production path exists.

## Factory creation accepts data it never writes

**[medium, confirmed]** `CreateFactoryDto` explicitly accepts `phoneNumber2`, `landline`, `fax`, `licenseExpiry`, `establishedDate`, and `employees`, all of which exist on the Prisma `Factory` model. The controller passes the validated DTO to `createFactory`, but the service omits those fields from its create data. Requests containing them succeed while their values become null or database defaults. Map the fields into the create data with date conversion, or remove them from the accepted create contract.

The DTO tests exercise gate-pass compatibility, moderation, extra-field rejection, and pagination. Not tested: factory create/update transformation or persistence, including the fields currently dropped by creation.
