# Canonical admin actor, correlated atomic audits, and scoped management validation

Task 3.5 now rebuilds every protected actor from the current database row, rejects malformed signed JWT subjects before Prisma, and gives management failures a shared correlation-aware envelope. User, park, and advertisement lifecycle writes use one transaction for the business mutation and success audit; moderation adds a scoped conditional transition, while dashboard/report queries preserve an explicit empty scope. The previous audit-correlation and factory-create persistence gaps are closed. The global exception filter still discloses messages from HTTP-shaped 5xx failures, the new envelope removes a legacy Nest field, and nested advertisement contact validation can be bypassed.

Watch for: **[high, confirmed]** HTTP 5xx exception messages are returned verbatim; **[medium, confirmed]** the global envelope drops the established `error` field; **[medium, confirmed]** supplying both contact phone aliases bypasses validation; **[medium, confirmed]** rollback, concurrent moderation, and request-to-audit correlation are covered only by mocks rather than a real request/database path.

**Verdict**: NEEDS_CHANGES

## High-level view

`JwtAuthGuard` now uses the JWT only to authenticate a bounded `sub`, then loads role, phone, active state, and approval state from Prisma. Stale role claims no longer authorize a request, deleted/inactive/unapproved users receive the same non-disclosing 401, and malformed signed subjects are rejected without a database call.

Request middleware establishes one validated or generated correlation ID before guards/controllers run, exposes it on the response, and stores it in `AsyncLocalStorage`. The audited transaction helper reads that context and writes the same ID with the successful audit inside the mutation transaction, so audit failure rejects the operation rather than reporting success.

The DTO boundary now constrains opaque IDs, enums, numbers, dates, and nested payloads while retaining both established advertisement phone aliases. Factory creation maps all newly accepted optional fields, including date conversion, but the cross-alias contact rule stops validating either phone when both aliases are present.

Advertisement moderation limits park managers at both lookup and conditional update, excludes unscoped advertisements, and allows only one `PENDING` transition to produce an audit. Dashboard and reports use `factoryId in []` for non-global actors with no scope, avoiding the previous fallback to global aggregation.

The exception filter supplies stable codes and correlation IDs for known failures and hides unknown exceptions. Its `HttpException` branch does not distinguish 4xx from 5xx, however, and reconstructs the response instead of extending the established Nest envelope.

## HTTP-shaped 5xx failures bypass the non-disclosing envelope

**[high, confirmed]** `ApiExceptionFilter` copies `HttpException.getResponse().message` for every HTTP status at `mekss-backend/src/core/api-exception.filter.ts:38-48`. A direct counterexample with `new InternalServerErrorException('database password=private')` returned `{"statusCode":500,"message":"database password=private","code":"HTTP_ERROR",...}`. Unknown `Error` objects are sanitized, but any controller, guard, interceptor, or library that wraps an internal failure as an `HttpException` can expose operational or credential-bearing detail. Route all status codes at or above 500 through the same fixed `INTERNAL_ERROR` body used for unknown exceptions.

## Rebuilt error responses remove the legacy Nest discriminator

**[medium, confirmed]** The same reconstruction at `mekss-backend/src/core/api-exception.filter.ts:38-48` keeps `statusCode` and `message` but discards the established `error` field. Before the filter, Nest serializes `BadRequestException(['bad field'])` as `{"message":["bad field"],"error":"Bad Request","statusCode":400}`; the new global response is `{"statusCode":400,"message":["bad field"],"code":"VALIDATION_ERROR","correlationId":...}`. This changes every existing error response despite the task’s backward-compatibility requirement. Preserve safe existing response fields and add `code`/`correlationId`, rather than replacing the prior envelope.

## Dual contact aliases disable each other’s validators

**[medium, confirmed]** `AdvertisementContactInfoDto` conditions `phone` validation on the absence of `phoneNumber` and vice versa at `mekss-backend/src/core/management.dto.ts:173-178`. When both properties are present, both `ValidateIf` predicates return false, so payloads such as `{ phone: 42, phoneNumber: 43 }` and `{ phone: 'x', phoneNumber: 'y' }` pass the production `ValidationPipe`. Keep backward compatibility by making each supplied alias independently optional-and-validated, then add a class-level requirement that at least one valid alias exists.

The current DTO test at `mekss-backend/src/core/management.dto.spec.ts:36-44` verifies each alias separately and an empty object, but never supplies both aliases, so it does not catch this bypass.

## Foundation guarantees are simulated rather than exercised

**[medium, confirmed]** The rollback test at `mekss-backend/src/core/management.service.spec.ts:9-34` implements `$transaction` as a callback invocation; it proves that audit failure is propagated but cannot prove that a preceding database write is rolled back. The moderation test at `mekss-backend/src/core/management.service.spec.ts:36-59` runs two calls sequentially and scripts `updateMany` counts, so it does not exercise simultaneous transactions or database isolation. Correlation is injected directly with `requestContext.run` rather than passing `X-Request-ID` through `requestContextMiddleware`, the controller, the transaction, and a committed audit row.

Add an isolated database/request integration test that observes no business row after audit failure, starts two moderation requests concurrently and observes one terminal transition plus one success audit, and verifies a successful request’s response header matches its committed `AuditLog.correlationId`. These are the principal regression guarantees of the new foundation and are not established by the current mocks.
