# Scoped, role-aware dashboard metrics and priority work

The dashboard retains its existing count fields and adds pending-work totals, capability identifiers, and a bounded priority feed. Tenant records are projected to safe fields, scoped before `take`, and query failures propagate to the existing 5xx envelope rather than becoming zeroes. The global emergency count matches the active schema and management emergency endpoint, neither of which has park/factory scope. **Watch for:** **confirmed, HIGH blocker** — materialized park-manager scope leaves a revocation race that can expose records and actions from a newly removed park; **confirmed, MEDIUM blocker** — generated integration evidence omits three authorized roles and the eight-item ordering boundary; **confirmed, MEDIUM blocker** — the scoped describe depends on an administrator fixture created by another describe.

**Result**: NEEDS_CHANGES — blocker severity: HIGH

**Verdict**: NEEDS_CHANGES

## High-level view

Super-admin aggregation remains global. Park-manager factory and advertisement scopes are applied before counts and recent-item limits, but they are resolved separately from the final reads, so a concurrent scope revocation can leave the response authorized by stale park IDs. Factory owners, security guards, and government officials retain their existing count and capability paths, while only super-admins and park managers receive review items.

Recent work uses explicit pending/scope predicates and safe projections, then merges into an eight-item feed ordered by request priority, timestamp, kind, and ID. The implementation is deterministic, but integration tests never cross the limit or assert tie ordering.

Open emergencies intentionally remain global because `EmergencyAlert` has no park/factory relation and the active emergency endpoint exposes the same global feed. Query failures are not converted to partial data or fabricated metrics.

The official integration runner provisions and drops an owned PostgreSQL schema and runs e2e files in band, containing the table-rename failure test. The scoped describe nevertheless relies on setup outside its boundary and lacks generated coverage for every authorized dashboard role.

3. **Cross-describe fixture dependency (confirmed, MEDIUM blocker)** — The scoped dashboard setup looks up an administrator created by another describe, so focused execution fails before dashboard assertions. Create all required actors inside the scoped describe.

## Materialized park IDs leave a scope-revocation window

**Confirmed, HIGH blocker.** `dashboard` reads the manager’s parks once, stores `managedParkIds`, then resolves factories and performs counts/recent reads from those IDs (`mekss-backend/src/core/management.service.ts:476-487`, `mekss-backend/src/core/management.service.ts:503-538`). A disconnect committed after line 476 leaves the removed park in `factoryScope` and `advertisementWhere`, allowing its counts, request/gate-pass/advertisement records, and mutation capabilities into the response.

The narrowing test commits its disconnect before starting the request (`mekss-backend/test/management-foundation.e2e-spec.ts:372-386`), so it cannot expose this interleaving. Enforce the current manager relation in the final record predicates and run scope resolution plus dashboard reads in one consistent database snapshot, giving authorization a clear linearization point.

## Generated contract evidence misses authorized roles and the limit boundary

The production queries put scope and `PENDING` predicates before `take: 8`, select only dashboard fields, and apply deterministic source and merged ordering (`mekss-backend/src/core/management.service.ts:514-577`).

**Confirmed, MEDIUM blocker.** The scoped describe signs tokens only for super-admin and park-manager actors (`mekss-backend/test/management-foundation.e2e-spec.ts:182-197`) and exercises only those roles (`mekss-backend/test/management-foundation.e2e-spec.ts:293-414`). Fixture factory owners never call the dashboard, and `SECURITY_GUARD` and `GOVERNMENT_OFFICIAL` are absent. Generated cases also contain at most six items and compare IDs as sets (`mekss-backend/test/management-foundation.e2e-spec.ts:324-369`), leaving the eight-item cap and equal-priority/equal-time ordering unproved. Add the missing role/scope matrix and an exact ordered assertion over more than eight tied fixtures.

## Scoped integration setup depends on another describe

**Confirmed, MEDIUM blocker.** The scoped `beforeAll` looks up phone `09121111111` (`mekss-backend/test/management-foundation.e2e-spec.ts:177-183`), but that user is created only by the transaction describe at lines 34-49. Focused execution with a test-name filter skips the other describe’s hook and fails in setup; changes to the unrelated transaction suite can also break dashboard evidence. Create the administrator within the scoped fixture.

The official runner otherwise contains the fixed identifiers and DDL failure injection in an owned schema, runs Jest in band, and drops the schema in `finally`. The request-table test restores the table in its own `finally` (`mekss-backend/test/management-foundation.e2e-spec.ts:416-431`).

## Global emergency and failure contracts

`openEmergencies` counts every non-resolved alert (`mekss-backend/src/core/management.service.ts:508`). This matches the schema’s unscoped `EmergencyAlert` model and the active global list at `mekss-backend/src/core/management.service.ts:468` / `mekss-backend/src/core/management.controller.ts:94`; tenant-specific emergency filtering would require a schema/API change.

The existing count fields retain their names and types, while `recentPriorityItems` is additive (`mekss-backend/src/core/management.service.ts:594-604`). Empty non-global scopes use `{ in: [] }`, and read failures escape the service without a fallback (`mekss-backend/src/core/management.service.ts:491-538`). Failure tests verify rejection and a 500 envelope without dashboard fields (`mekss-backend/src/core/management.service.spec.ts:220-234`, `mekss-backend/test/management-foundation.e2e-spec.ts:416-431`).

Targeted validation passed: `npm test -- --runInBand core/management.service.spec.ts` (8 tests), `npm run typecheck -- --pretty false`, and check-only ESLint over the affected files. E2e execution was not run because `MEKSS_TEST_DATABASE` and `DATABASE_URL` are unset; the safety gate correctly blocks non-owned databases.
