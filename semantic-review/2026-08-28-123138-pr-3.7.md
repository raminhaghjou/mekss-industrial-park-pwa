# CRUD تراکنشی شهرک صنعتی با حفاظت رابطه‌ای

این تغییر مرز typed برای CRUD شهرک را کامل می‌کند، list را در snapshot تکرارپذیر می‌خواند و create/update/delete را با audit در یک transaction قرار می‌دهد. تخصیص مدیر فقط برای `PARK_MANAGER` فعال و تأییدشده پذیرفته می‌شود و delete همه‌ی روابط مستقیم موردنظر را پیش از حذف بررسی می‌کند؛ FKهای announcement، advertisement، guard و feedback نیز restrictive شده‌اند. پاسخ‌های موفق قبلی حفظ شده‌اند و relation/countهای جدید به‌صورت افزایشی برمی‌گردند. دو بخش از معیار اثبات نشده‌اند: collision کد در update و اجرای migration روی داده‌ی واقعاً legacy. **Watch for:** **confirmed** — migration فقط با بازرسی متن SQL بررسی شده و روی snapshot پرشده‌ی قبل از migration اجرا نمی‌شود؛ **confirmed** — uniqueness کد mutable فقط در create تحت race آزموده شده و مسیر update collision/rollback پوشش ندارد.

**Result**: NEEDS_CHANGES

**Blockers**: اجرای migration روی legacy snapshot و تست collision کد در update.

**Verdict**: NEEDS_CHANGES

## High-level view

DTOهای create/update رشته‌های اجباری را trim، optionalهای خالی را `null`، تاریخ و عدد را typed و status را با enum canonical محدود می‌کنند. list/detail/create/update scalarها و manager projection قبلی را نگه می‌دارند و countهای جدید را اضافه می‌کنند؛ code نیز اکنون عمداً mutable است.

list، rows و total را در یک `RepeatableRead` transaction می‌گیرد و tie مربوط به `createdAt` را با `id` می‌شکند. create/update پس از write representation مشترک را در همان transaction دوباره می‌خوانند و audit failure کل mutation را rollback می‌کند.

managerها پیش از assignment با row lock و role/active/approved canonical بررسی می‌شوند. delete نیز park را `FOR UPDATE` قفل می‌کند، factory/manager/announcement/advertisement/guard/file/feedback را می‌شمارد و P2003 نهایی را به 409 تبدیل می‌کند؛ تغییر lifecycle بعدی manager مربوط به Task 3.8 است و blocker این review نیست.

SQL جدید business data را rewrite نمی‌کند و orphanهای قبلی feedback را با `NOT VALID` حفظ می‌کند، اما **confirmed** safety واقعی upgrade تست نشده است. تست‌های CRUD گسترده‌اند، ولی **confirmed** update کد mutable در حالت duplicate/concurrent و عدم audit برای loser را نمی‌پوشانند.

## Snapshot، committed representation و mutable-code conflict

list با `createdAt DESC, id ASC` tie پایدار دارد و `items`/`total` را در یک `RepeatableRead` transaction تولید می‌کند (`mekss-backend/src/core/management.service.ts:91-112`). create و update فقط فیلدهای حاضر را می‌نویسند، relation/countها را از همان transaction دوباره می‌خوانند و helper مشترک پیش از commit دقیقاً یک AuditLog درج می‌کند (`mekss-backend/src/core/management.service.ts:119-184`, `mekss-backend/src/core/management.service.ts:766-781`). trigger-based e2e شکست audit را برای هر سه mutation تحمیل و rollback park/audit را بررسی می‌کند (`mekss-backend/test/park-management.e2e-spec.ts:343-392`).

**confirmed** uniqueness فقط با دو create هم‌زمان و retry create آزموده می‌شود (`mekss-backend/test/park-management.e2e-spec.ts:216-253`). هیچ تستی دو park موجود را به یک code trimmed update نمی‌کند یا ثابت نمی‌کند loser با 409، state قبلی و بدون `PARK_UPDATED` audit باقی می‌ماند. برای بستن blocker، دو `PUT` هم‌زمان با variantهای whitespace یک code بفرستید و دقیقاً یک موفقیت، یک conflict و یک owner نهایی code را assert کنید.

## Linearization تخصیص manager و حذف محافظت‌شده

قبل از connect/set، شناسه‌های manager یکتا می‌شوند، user rowها با `FOR SHARE` قفل می‌شوند و count فقط role=`PARK_MANAGER` همراه با `isActive=true` و `isApproved=true` را می‌پذیرد (`mekss-backend/src/core/management.service.ts:245-254`). این ترتیب assignment را نسبت به mutation هم‌زمان user خطی می‌کند: mutation زودتر-commit‌شده در count دیده می‌شود و mutation دیرتر تا پایان transaction منتظر می‌ماند.

delete row شهرک را `FOR UPDATE` می‌گیرد و factory، manager، announcement، advertisement، security guard، scoped file و feedback را در همان transaction بررسی می‌کند (`mekss-backend/src/core/management.service.ts:187-224`). FKهای factory/scoped-file از قبل restrictive هستند و migration سه delete action ناامن را به RESTRICT تبدیل و FK feedback را restrictive اضافه می‌کند (`mekss-backend/prisma/migrations/20260828000100_park_delete_integrity/migration.sql:5-25`). direct-FK e2e حفظ relation را بعد از delete ردشده اثبات می‌کند و unit test مسیر P2003 race را به 409 pin می‌کند (`mekss-backend/test/park-management.e2e-spec.ts:284-340`, `mekss-backend/src/core/management.service.spec.ts:345-416`). join ضمنی manager در DB cascade است، اما manager count همراه با parent-row lock مانع رسیدن API delete به آن cascade می‌شود.

## Legacy upgrade بدون شواهد اجرایی

سه relation تغییرکرده از قبل FK معتبر داشته‌اند؛ feedback که قبلاً FK نداشته با `NOT VALID` اضافه می‌شود تا orphan تاریخی migration را fail نکند و write جدید و delete park دارای feedback محدود شود (`mekss-backend/prisma/migrations/20260828000100_park_delete_integrity/migration.sql:1-26`).

**confirmed** `park-delete-migration.contract.spec.ts` فقط schema/SQL را به‌صورت string بررسی می‌کند و integration runner تمام migrationها را روی schema خالی اعمال می‌کند؛ هیچ مسیر تستی ابتدا migration قبلی را اعمال، park و relationهای معتبر به‌علاوه orphan feedback را درج و سپس migration جدید را اجرا نمی‌کند (`mekss-backend/src/preservation/park-delete-migration.contract.spec.ts:1-39`, `scripts/run-backend-integration.mjs:74-92`). برای بستن blocker، schema disposable را تا `20260828000000_schema_alignment` migrate کنید، fixtureهای legacy را seed کنید، `20260828000100_park_delete_integrity` را اعمال و حفظ رکوردها، پذیرش orphan قدیمی، رد orphan جدید و RESTRICT delete را بررسی کنید.
