# Safe transactional user administration lifecycle

Task 3.8 replaces permissive user-management writes with validated DTOs, no-secret projections, serialized lifecycle transactions, durable assignment checks, audit-coupled mutations, and `sessionVersion` invalidation. Administrative quorum, no-op, protected-delete, and audit rollback handling are substantially stronger. The change is not safe to ship because token issuance is not serialized with access changes, allowing concurrent login or refresh to leave a usable replacement refresh token after revocation. Frontend refresh coordination, the edit-password contract, canonical uniqueness, and required race/deletion evidence also remain incomplete.

**Watch for:** **confirmed, HIGH** — concurrent login/refresh can survive password reset or access change with a usable refresh token; **confirmed, MEDIUM** — parallel browser 401s can clear a successfully rotated session; **confirmed, MEDIUM** — edit-user sends a `password` field rejected by PATCH; **confirmed, MEDIUM** — lowercasing inputs does not make existing case-sensitive unique indexes canonical; **confirmed, MEDIUM** — database evidence omits token-issuance races and most protected relations and could not be executed here.

**Task 3.8 result**: FAIL

**Verdict**: NEEDS_CHANGES

## High-level view

Managed-user responses use allowlisted Prisma projections, while create/update/reset contracts normalize identities, preserve password bytes, and reject incompatible park, factory-owner, and employee assignments. Raw text uniqueness still allows normalized writes to coexist with pre-existing mixed-case email or username records.

Administrative mutations take a transaction-wide advisory lock, re-read the acting administrator, lock the target, and write the success audit in the same transaction. This closes the final-active-approved `SUPER_ADMIN` race and makes repeated state requests no-ops, but login, OTP login, and refresh remain outside that lock boundary.

Hard deletion protects business relations, cascades refresh/OTP artifacts, and detaches `AuditLog.userId` while retaining `actorIdentifier`. The migration permits only the FK-style `userId -> null` audit update, and the target lock prevents late protected-relation inserts from disappearing.

The browser stores rotated refresh tokens and preserves administrator-entered password whitespace. It still launches one refresh per failed request, and the edit form retains an inline password field that the validated PATCH endpoint no longer accepts.

Static checks and focused tests pass. The disposable-database E2E runner lacked its explicit environment opt-in, and its committed scenarios are sequential around revocation and exercise only one protected relation.

Auth similarly replaces `Omit<User, 'password'>` with an explicit `Pick` and object projection, excluding `sessionVersion`, `bootstrapKey`, refresh tokens, and OTP challenges (`mekss-backend/src/core/auth.service.ts:10-32`, `:198-220`). E2E assertions cover list, detail, create, and password-reset responses (`mekss-backend/test/user-management.e2e-spec.ts:31-35`, `:99-143`, `:247-253`).

**Confirmed, MEDIUM:** DTOs lowercase email/username and normalize phone/national ID (`mekss-backend/src/core/management.dto.ts:28-50`, `:85-117`), but the schema retains case-sensitive `@unique` indexes (`mekss-backend/prisma/schema.prisma:180-192`) and the Task 3.8 migration adds no canonical constraints (`mekss-backend/prisma/migrations/20260828000200_user_session_version/migration.sql:1-24`). Add a collision-detecting migration and canonical constraints/indexes, or enforce canonicalization at every writer.

## Assignment and super-admin invariants share one lifecycle lock

Create/update enforce mutually exclusive park-manager, factory-owner, and employee assignment shapes and validate targets (`mekss-backend/src/core/management.service.ts:119-249`, `:1027-1064`). Factory ownership must be reassigned before removal; park and employee assignments can be cleared. The advisory lock, acting-account re-read, and target `FOR UPDATE` serialize management mutations before final-admin checks (`mekss-backend/src/core/management.service.ts:971-1011`).

Access-changing updates, activation changes, and admin password resets increment `sessionVersion`, revoke refresh tokens, and append one audit in the transaction (`mekss-backend/src/core/management.service.ts:251-272`, `:293-321`). ## Concurrent token issuance can resurrect a revoked session

**Confirmed, HIGH:** password login validates a `User` and later calls `issueTokens` without the management target lock or a transaction (`mekss-backend/src/core/auth.service.ts:55-62`, `:178-190`). Refresh rotation compare-and-swaps the consumed token, but does not lock the user against `sessionVersion` changes before creating its replacement (`mekss-backend/src/core/auth.service.ts:117-139`). Management locks and updates the user before `refreshToken.updateMany` (`mekss-backend/src/core/management.service.ts:263-267`, `:303-319`, `:988-992`), but that statement need not see a token inserted by an already-running issuer.

```text
login(old password)             admin reset-password
-------------------             --------------------
read user at sessionVersion 0
validate old password
                                lock user; set version 1
                                revoke visible refresh tokens; commit
create refresh token after revocation
refresh it -> load version 1 -> mint valid access
```

`JwtAuthGuard` rejects the stale initial access token (`mekss-backend/src/core/auth.guard.ts:26-46`), but the surviving refresh token is not epoch-bound and can mint a current token. The refresh path can produce the same result when its claim overlaps revocation. Serialize all token issuers with the user row and reload after locking, or persist and enforce the issue epoch on refresh tokens. Add login-vs-reset, refresh-vs-reset, and refresh-vs-deactivation races.

## Protected deletion retains history and detaches only the audit actor FK

Refresh tokens and OTP challenges cascade; audit logs remain via `ON DELETE SET NULL` (`mekss-backend/prisma/schema.prisma:589-621`, `:730-750`; `mekss-backend/prisma/migrations/20260817000000_initial_schema/migration.sql:198-200`). The trigger exception permits only non-null-to-null `userId` with every other audit column unchanged (`mekss-backend/prisma/migrations/20260828000200_user_session_version/migration.sql:9-24`).

The E2E suite confirms notification retention, auth-artifact deletion for an eligible user, audit detachment, exactly one deletion audit, and rollback when audit insertion fails (`mekss-backend/test/user-management.e2e-spec.ts:282-343`).

## Browser rotation and password-reset UI have two contract failures

**Confirmed, MEDIUM:** every 401 independently reads the same refresh token and calls `/auth/refresh`; no in-flight promise coordinates requests (`mekss-industrial-park/src/services/api/base.api.js:38-70`). With concurrent 401s, one backend rotation succeeds and one fails; the loser then removes the winner’s stored pair and redirects. Use a single-flight refresh queue and clear storage only when that shared attempt fails. Add a two-401 interceptor test asserting one refresh, two retries, and retained rotated tokens.

**Confirmed, MEDIUM:** PATCH now validates `UpdateManagedUserDto`, which has no password member (`mekss-backend/src/core/management.controller.ts:41-45`; `mekss-backend/src/core/management.dto.ts:100-117`). The reset dialog opts out of trimming (`mekss-industrial-park/src/pages/superadmin/ManageUsersPage.jsx:212-225`; `mekss-industrial-park/src/components/common/ConfirmDialog.jsx:23-38`), and E2E proves whitespace remains credential data (`mekss-backend/test/user-management.e2e-spec.ts:247-258`).
