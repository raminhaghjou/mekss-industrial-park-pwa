## User-row serialization closes refresh resurrection but misses phone identity turnover

Password login locks the candidate user, reloads credentials and account state, and creates the refresh token in the same transaction (`mekss-backend/src/core/auth.service.ts:56-66`). OTP login uses the same boundary (`:90-98`), while refresh locks the user before reading and claiming the token (`:132-154`). Administrative mutations take the lifecycle advisory lock before the target user lock and revoke refresh tokens after updating access state (`mekss-backend/src/core/management.service.ts:976-993`, `:264-267`, `:303-305`, `:314-319`). Auth paths never acquire that advisory lock, and every path touching both resources takes `User` before `RefreshToken`, closing the prior resurrection race without a lock-order cycle.

**Confirmed, MEDIUM:** password login resolves the candidate by submitted phone before taking the lock, then reloads only by user ID and never verifies that the locked row still has that phone (`mekss-backend/src/core/auth.service.ts:56-65`). OTP verification consumes a challenge keyed by the old phone before locking, then also reloads only by user ID (`:90-98`, `:182-198`). A management phone change increments `sessionVersion` and revokes refresh tokens, but does not consume outstanding OTP challenges (`mekss-backend/src/core/management.service.ts:220-267`).

```text
old-phone OTP issued             administrator changes phone
--------------------             ---------------------------
challenge stores old phone
                                 lock user; write new phone
                                 increment epoch; revoke refresh
verify OTP using old phone
lock/reload user by id
mint current-epoch tokens
```

The OTP remains usable until expiry after the old number is no longer the account identifier; a password login that resolved the old number immediately before the change can similarly complete afterward. Recheck `user.phoneNumber === phoneNumber` while holding the lock, and invalidate login OTP challenges by `userId` on phone changes or bind challenges to `sessionVersion`.
