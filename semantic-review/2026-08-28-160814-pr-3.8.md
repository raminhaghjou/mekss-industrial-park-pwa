# Serialized user administration with identity-bound session invalidation

Task 3.8 replaces permissive user writes with validated lifecycle contracts, user-row serialization, access-token epochs, refresh revocation, exact-once transactional audits, protected-delete checks, and no-secret response projections. The previous password-login and OTP-login old-phone races are fixed by reloading and comparing the submitted phone while holding the user lock, and phone updates revoke current sessions and consume existing unconsumed OTPs in the same transaction. The implementation is still unsafe to ship because reset OTP issuance is not serialized with phone changes and password reset does not revalidate the phone after taking the user lock. An old number can therefore receive a new reset challenge after the account has moved and use it to replace the password.

**Watch for:** **confirmed, HIGH** — concurrent old-phone password-reset issuance can escape the phone-change OTP sweep, and the reset path accepts that old identity after locking the renamed user; serialize OTP issuance with the user row and revalidate the submitted phone in the reset transaction.

**Verdict**: NEEDS_CHANGES

## High-level view

Management mutations share a transaction-wide lifecycle gate, revalidate the acting administrator, lock the target user, and only then update refresh tokens. This preserves the final active approved super-admin invariant, establishes the User → RefreshToken order, and couples each effective mutation to one audit while leaving no-ops unaudited.

Password login, OTP login, and refresh rotation now follow the same user-first boundary, so issuance either commits before an access change and is subsequently invalidated or observes the changed account state. **confirmed:** password-reset OTP issuance remains outside that boundary, and reset consumption does not compare the submitted phone with the locked user.

Managed-user DTOs canonicalize identities, enforce password and role-assignment shapes, and responses use explicit public projections. The migration rejects ambiguous legacy identity collisions, canonicalizes safe values, adds the session epoch, and preserves audit history when an eligible user is deleted.

The frontend single-flights concurrent refresh attempts, persists both rotated tokens, and separates edit-user fields from the dedicated password-reset operation. The supplied validation covers the backend, migration contracts, generated preservation properties, PostgreSQL lifecycle races, frontend, and build checks, but the old-phone E2E races password login and login OTP rather than reset-OTP issuance and password reset.

## Old-phone login closure leaves password reset able to recreate trust

Password login and OTP login now verify `user.phoneNumber === phoneNumber` after `FOR UPDATE` (`mekss-backend/src/core/auth.service.ts:56-68`, `:91-101`). The phone PATCH increments `sessionVersion`, revokes live refresh tokens, and consumes every currently visible unconsumed OTP purpose while holding the target user lock (`mekss-backend/src/core/management.service.ts:252-275`).

**confirmed, HIGH:** `sendOtp` reads the user by old phone without locking it, then creates the challenge in a later transaction (`mekss-backend/src/core/auth.service.ts:71-88`). A phone PATCH can commit its OTP `updateMany` before that transaction inserts a `PASSWORD_RESET` challenge, leaving a fresh unconsumed old-phone challenge after the sweep. `resetPassword` consumes that challenge before obtaining the user lock and, unlike OTP login, never checks the current `user.phoneNumber` against the submitted phone before updating the password and epoch by ID (`mekss-backend/src/core/auth.service.ts:103-115`).

```text
/password/forgot(old phone)       PATCH user phone
--------------------------       ----------------
resolve user by old phone
                                 lock User
                                 write new phone + increment epoch
                                 revoke refresh + consume visible OTPs
                                 commit
create PASSWORD_RESET challenge
send OTP to old phone
/password/reset(old phone, OTP)
consume challenge; lock User by id
replace password on new-phone account
```

Serialize challenge replacement and creation with the same user row, reload and compare the submitted phone after locking, and keep challenge creation inside that transaction. Password reset must also reload the locked user and reject when its current phone differs. Add deterministic `/password/forgot` versus phone-PATCH and `/password/reset` versus phone-PATCH races; the current PostgreSQL case creates both challenges before PATCH and invokes `/auth/login` plus `/auth/otp/verify`, so it cannot detect this post-sweep reset challenge (`mekss-backend/test/user-management.e2e-spec.ts:339-409`).

## Lifecycle serialization and exact-once mutation boundaries

`userLifecycleTransaction` combines the lifecycle advisory lock, acting-admin revalidation, and target `FOR UPDATE` lock in one boundary (`mekss-backend/src/core/management.service.ts:976-1017`). Access-changing updates, activation changes, administrative password resets, and authentication paths that touch refresh state all acquire User before RefreshToken. Final-admin checks run inside the same serialized boundary as demotion, deactivation, and deletion.

Effective changes insert their audit in the mutation transaction, while identical updates and repeated activation return without an audit plan. Protected deletion checks business relations and translates late foreign-key races to conflict; authentication artifacts cascade, while retained audit rows detach only the nullable user key and keep the durable actor identifier.

## Assignment, secrecy, migration, and browser contracts

Create/update contracts normalize unique identities and enforce role-compatible park, factory-owner, and employee relationships. Factory ownership cannot be silently removed through the user endpoint, while park and employee assignments can be explicitly replaced or cleared. Allowlisted response projections omit passwords, session epochs, bootstrap keys, token records, and OTP challenges.

The migration fails before canonicalization when case/whitespace-equivalent identities would collide, then constrains future email and username writes to canonical storage. The frontend queues parallel 401 retries behind one refresh promise, stores the rotated access and refresh pair before retrying, removes `password` from user edits, and preserves exact password bytes for the dedicated reset contract.
