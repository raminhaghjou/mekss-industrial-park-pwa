# Serialized user administration and old-phone trust invalidation

Task 3.8 replaces permissive user writes with validated transactional lifecycle operations, explicit safe projections, assignment checks, session epochs, refresh revocation, protected deletion, and exact-once management audits. The final fix closes the reported old-phone password-reset race by putting OTP issuance behind the same user-row serialization boundary as phone changes and revalidating the submitted phone after reset acquires that boundary. Both serialization orders leave no post-change old-phone credential usable, and no confirmed blocker remains across the management, migration, auth, or frontend contracts.

**Watch for:** no confirmed actionable blockers remain; the previously reported old-phone PASSWORD_RESET takeover is materially closed.

**Verdict**: APPROVED

## High-level view

OTP issuance now locks and reloads the candidate user before replacing a challenge. Password reset claims a challenge exactly once, then locks and revalidates the user before changing credentials; phone PATCH uses the same user-first boundary and consumes every outstanding OTP purpose.

User administration serializes lifecycle mutations, revalidates the acting super-admin, and preserves the acting-account and final-active-approved-super-admin invariants. Access changes advance the token epoch and revoke refresh tokens, while no-ops avoid writes and audits.

Managed-user DTOs canonicalize identities, preserve password bytes, and constrain assignments by role. Responses are allowlisted projections, pagination uses a deterministic repeatable-read snapshot, and protected relationships prevent unsafe hard deletion.

The migration refuses ambiguous legacy canonicalization while adding the session epoch and audit-detachment support. The frontend single-flights concurrent refreshes, persists the complete rotated pair, and keeps password changes in the exact-byte reset flow.

## Old-phone issuance and reset share the phone-change boundary

The previous blocker is **confirmed closed** in `mekss-backend/src/core/auth.service.ts:70-96` and `:113-129`. `sendOtp` uses its initial lookup only to identify the row, then takes `User FOR UPDATE`, reloads by ID, compares the current phone, and replaces the same-purpose challenge inside that transaction. `resetPassword` exact-once claims the submitted PASSWORD_RESET challenge, takes the user lock, reloads and compares the phone, rechecks active/approved state, then changes the password, advances `sessionVersion`, revokes refresh tokens, and writes the audit in one credential-change transaction.

Phone PATCH takes the lifecycle advisory lock and target `User` row before changing the number, then advances the epoch, revokes refresh tokens, and consumes all unconsumed challenges by `userId` without filtering by purpose (`mekss-backend/src/core/management.service.ts:252-276`, `:976-1017`). Both orders are closed:

```text
OTP issuance/reset wins User lock     Phone PATCH wins User lock
---------------------------------     --------------------------
validate old phone                    write new phone + epoch
create/claim old-phone challenge      revoke refresh + consume all OTPs
optionally reset password + epoch     commit
commit                                old-phone reload rejects
phone PATCH consumes/revokes          no old-phone reset is applied
```

There is no opposing lock chain. Issuance and phone PATCH acquire `User` before OTP rows; reset's exact-once claim completes before its credential transaction, so it retains no OTP lock while waiting for `User`. Login and refresh also acquire `User` before refresh-token writes. The PostgreSQL race covers phone PATCH against old-phone password login, LOGIN OTP, reset issuance, and reset consumption, then verifies no raced password was installed and no old-phone challenge remains (`mekss-backend/test/user-management.e2e-spec.ts:339-420`).

## Administrative invariants share one mutation boundary

`userLifecycleTransaction` takes one transaction-scoped advisory lock, rechecks the actor from the database, and locks the target row before evaluating lifecycle state. This prevents concurrent removal of the final two eligible super-admins, blocks acting-account deletion/deactivation/demotion/unapproval, and keeps the lock order at `User` before auth artifacts.

Role transitions and assignment changes are evaluated as one final state. Park, factory-owner, and employee assignments cannot survive incompatible roles, and required factory ownership cannot be silently disconnected. Identical updates and repeated activation do not change timestamps, epochs, or audits; effective mutations and their single audit commit or roll back together.

## Safe projections, deletion, and migration preservation

List and detail queries explicitly select public lifecycle and relationship fields. Password hashes, session epochs, bootstrap state, tokens, and OTP challenges are absent from every managed-user response, while equal timestamps receive a stable ID tiebreaker and rows plus total share one repeatable-read snapshot.

Protected business relationships are checked inside the locked deletion transaction, and late foreign-key races become `409` without a deletion or audit. Eligible deletion removes auth artifacts while retained append-only audits detach only the nullable user key and preserve the durable actor identifier.

The migration rejects case/whitespace-equivalent legacy email or username collisions before normalization, adds canonical-storage and nonnegative-epoch constraints, and narrows its audit-trigger exception to referential `userId` detachment. Database uniqueness remains authoritative for concurrent identity creation.

## Browser session and password contracts

The refresh interceptor shares one promise across concurrent 401s, validates and stores both rotated tokens before retrying through the configured client, and clears both on failure. User edits omit `password`; the dedicated reset dialog disables trimming, matching backend DTOs that hash the exact submitted bytes.
